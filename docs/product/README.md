# 产品形态与商业模式

本文记录栖灵 Animus 在产品形态（服务端/客户端分离）与收费模式上的决策思考。
结论先行的三条主线：**协议边界已完成、部署分离值得做、按"活性"分级收费**。

## 1. 客户端语言选择（决策记录）

桌宠/游戏 demo 客户端**现阶段留在 Python**：

- 桌宠客户端是纯 I/O 负载（WS 帧进出 + 单精灵渲染 + 气泡排版），重活（LLM、编剧、
  导演、议程）全在服务端；换语言的收益感知不到
- 桌宠现阶段的核心用途是**验证 soul 主体性行为**（沉默/主动/预约的表现力），
  迭代频率高，Python 改一行见效
- 换语言的真实代价：用新语言重写一遍协议客户端（`src/client/speak_ws.py`、
  WebUI `static/js2/protocol/` 已摸通全部帧语义）

**产品化触发条件**（满足其一再换）：需要分发给非开发者用户。届时推荐
Rust + Tauri（per-pixel alpha、点击穿透、小体积单 exe）或 C#/WPF（Windows 原生
分层窗口）；Electron 不考虑（桌宠吃 150MB 内存与产品隐喻相悖）。

近期客户端侧唯一值得动的点：色键透明（品红镂空）换成 `UpdateLayeredWindow`
per-pixel alpha，消除气泡抗锯齿毛边。

## 2. 服务端/客户端分离

**代码层面的分离已经完成**：WebUI 前端 `static/js2/protocol/`（frames /
agent_events / speak_fields）+ Python 侧 `src/client/speak_ws.py` + 服务端帧协议
（session_open / speak_event / typing_pulse / proactive_ack）构成干净的
client-server 契约。桌宠连 `127.0.0.1` 还是连云端，代码一行不改。

因此"彻底分离"真正要补的是**部署分离**，不是代码分离：

- 服务端无头化运行（FastAPI + WS 已具备，缺配置入口）
- 鉴权层：账号 token（任何远程客户端接入的前提）
- 客户端可配置服务器地址（桌宠/WebUI 默认 localhost，可指向云端）

明确不做的事：**不要 fork 出"游戏 demo 服务端"和"桌宠服务端"两套代码**。
多客户端是本产品的 feature 而非负担——同一 soul 的多张脸：

| 客户端 | 定位 |
|---|---|
| WebUI | 控制室（配置、记忆、人格、调度、监控） |
| 桌宠 desktop_pet | 陪伴的脸（主体性行为可视：沉默「…」、主动「💬」、眯眼等待） |
| pygame_town | 模拟沙盒（多 agent 社交与剧情验证） |
| bot / bark / ntfy | 出站触达渠道 |

## 3. 部署形态取舍

| 形态 | 优势 | 代价 |
|---|---|---|
| 本地（soul 跑在用户机器） | 隐私最优（记忆是最私密数据）；零边际成本 | "常驻"是假的：关机即停摆，heartbeat/presence/poll 全部休眠 |
| 云端（soul 住服务器） | 字面意义的常驻：关机后她仍在生活；主动性价值完全兑现 | 记忆隐私、推理成本、运维负担 |
| **混合（推荐）** | 同一套代码两种部署：本地免费底座 + 云端订阅 | 需要账号/鉴权/计费钩子 |

选择混合即不做非此即彼的产品决策；服务端无头化 + token 鉴权这一步做完，
本地/云端只是同一产品的两种安装方式。

## 4. 成本结构与收费模式

关键事实：**主动性 = token 燃烧**。poll 阶梯、presence 扫描、议程到点、
enter greeting 每一次都是真实推理成本，且发生在用户不在场时。由此推出两条原则：

1. 免费档必须节流主动性（拉长 poll 间隔、关闭部分扫描），否则成本不可控
2. **定价维度 = 活性等级，永远不按消息条数收费**——按条收费会让用户"节省和她的
   对话"，是对陪伴关系幻觉的谋杀

### 活性分级订阅（云端形态）

| 档位 | 隐喻 | 能力 |
|---|---|---|
| 免费 | 她在沉睡 | 可对话；poll 稀疏；无主动开场；记忆浅 |
| 标准 | 她醒着 | 完整主动性链路 + 常驻记忆 |
| 高阶 | 她在生活 | + 长程预约（speak 路径接入 scheduler）+ 云端常驻（关机后仍活着）+ 记忆云备份 + 跨设备在场 |

付费点恰好是成本点：主动性烧 token，就为"活性"收费。本地免费 + BYO API key
作为获客底座（现有架构零改动）；精品人格包 / 桌宠形象作为后续增值；
云端订阅作为收入主体。

### 风险提示

- 陪伴类产品在国内有 AIGC 合规成本（内容审核、实名）；出海相对干净
- "她一直在生活" = 为每个付费 soul 提供 7×24 进程；单用户托管成本须先核算再定价

## 5. 落地顺序（技术侧）

1. 服务端无头化 + token 鉴权（薄层）
2. "活性等级"做成服务端配置：poll 阶梯 / presence 扫描的档位开关
3. 桌宠加"服务器地址 + token"连接设置
4. speak 对话路径接入长程预约（补齐时间层主体性缺口，见
   `docs/agent/soul/README.md` 的主体性审计）

三步完成后，产品同时具备本地与云两种卖法。
